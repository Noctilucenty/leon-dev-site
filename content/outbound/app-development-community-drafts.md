<!-- app-community-draft: mvp-scope -->
### 2. MVP-scope teardown — founder question

**Title A:** A simple way to cut an app MVP before writing code

**Title B:** Which feature proves the app idea—and which can wait?

**Body:**

> A useful first app version is not every feature at lower quality. It is one
> complete loop: the user has a reason to open it, finishes one valuable action,
> and the business can handle what happens next.
>
> I would sort a feature list into three columns: required for that loop,
> required for safety or store review, and later. Accounts, payments, chat,
> dashboards, and AI can all be valid, but they should not enter version one
> just because other apps have them.
>
> I am Leon Kelvin Li, the developer behind Leon Builds. I build the app and the
> backend when both are needed. Post a one-sentence user/action description and
> I can suggest what I would test before expanding the scope.
>
> `[OPTIONAL LINK ONLY IF CURRENT RULES ALLOW — USE mvp-scope URL]`

<!-- app-community-draft: build-or-buy -->
### 3. Build-or-buy decision — small-business discussion

**Title A:** When a small business should not commission a custom app

**Title B:** Custom app, existing software, or mobile website?

**Body:**

> I would not start with “we need an app.” I would start with the repeated job:
> booking, field updates, customer status, membership access, ordering, or an
> internal approval. Then compare three options:
>
> - Can an existing tool handle it without forcing a bad workflow?
> - Can a mobile website handle it without an install?
> - Does a custom app add something genuinely useful, such as notifications,
>   offline work, device features, or frequent repeat use?
>
> I build websites, workflows, and mobile apps through Leon Builds, so the goal
> is to choose the smallest sensible format—not force every problem into an app.
> What repeated task are you trying to make easier?
>
> `[OPTIONAL LINK ONLY IF CURRENT RULES ALLOW — USE build-or-buy URL]`
